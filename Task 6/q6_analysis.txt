1. WORK OUT (RTT = 100 ms)
--------------------------------------------------------------------------------
(a) Handshake Time Before First Application Request Byte:
    - TCP + TLS 1.2: 1 RTT (TCP) + 2 RTT (TLS 1.2) = 3 RTT = 300 ms
    - TCP + TLS 1.3: 1 RTT (TCP) + 1 RTT (TLS 1.3) = 2 RTT = 200 ms
    - QUIC (First Visit): Combined transport + TLS 1.3 = 1 RTT = 100 ms
    - QUIC (0-RTT Resumption): Application data in flight 1 = 0 RTT = 0 ms

(b) 0-RTT Replay Attack Risk & Safe vs. Unsafe Operations:
    - Risk: 0-RTT packets are encrypted with a cached resumption PSK before the
      server provides fresh randomness. An attacker can capture and replay the
      0-RTT packet to duplicate actions.
    - Never use 0-RTT for non-idempotent state-changing requests (fund transfers,
      bill payments, beneficiary additions, password resets).
    - Safe for 0-RTT: Read-only, idempotent GET requests (checking account
      balance, viewing branch/ATM locations, fetching public exchange rates).

(c) QUIC Connection Migration (Wi-Fi -> 5G):
    - TCP ties connections to the 4-tuple (Source IP, Source Port, Dest IP, Dest
      Port). Switching from Wi-Fi to 5G changes the client IP, breaking the socket
      and forcing a full reconnect.
    - QUIC identifies connections using a cryptographic 64-bit Connection ID (CID)
      in the packet header, allowing seamless migration across IP/port changes
      without dropping session state or re-handshaking.

(d) Enterprise Firewall Blocking UDP 443 & Fallback:
    - Many enterprise firewalls block outbound UDP port 443 to prevent DDoS
      amplification or uninspected traffic.
    - Solution: Implement Happy Eyeballs fallback—attempt QUIC (UDP 443) first,
      and automatically race a TCP + TLS 1.3 connection if no QUIC response
      arrives within 100-200 ms.

2. CONCLUSION
--------------------------------------------------------------------------------
Yes, the bank's mobile app should deploy QUIC with Happy Eyeballs TCP + TLS 1.3
fallback. It cuts initial connection setup latency by 50% (100 ms vs. 200 ms)
and eliminates dropped sessions when customers move between Wi-Fi and cellular.

3. ALTERNATIVE CONCEPT ANALYSIS (WI-FI TO 5G SWITCH MID-TRANSFER AT RTT = 100 ms)
--------------------------------------------------------------------------------
- TCP + TLS 1.3:
  1. Experiences RTO detection delay (~500-1,000 ms) on the dead Wi-Fi socket.
  2. Opens new TCP socket on 5G (1 RTT = 100 ms).
  3. Performs TLS 1.3 session resumption handshake (1 RTT = 100 ms).
  4. Re-sends HTTP Range request for interrupted bytes (1 RTT = 100 ms).
  -> Loses at least 300 ms in handshake/request RTTs plus RTO detection delay,
     and risks duplicate transaction submission if POST status was unacknowledged.
- QUIC:
  1. Immediately transmits next packet from 5G IP carrying the same Connection ID.
  2. Server validates new path via PATH_CHALLENGE / PATH_RESPONSE (1 RTT) while
     continuing data transfer without resetting congestion state.
  -> 0 ms session re-establishment delay; zero dropped application requests.
